================================================================================
CLAIM 2 -- the merged-object mechanism: why those 4 can't be single-seed sound
================================================================================

Instrumentation (THROWAWAY, reverted -- see below): main.go's ENGINE FOOTPRINT
loop already computes, per mismatching receiver r, the MISSING objects
(batch[r] minus demand[r].pts). A new DUMPBASE-gated block groups those missing
objects by their own base id (`de.base[o]`, a static array independent of
query state) and, for the top-3 bases by missing-object count per receiver,
measures two things:

  (a) |storesWhereValue[base]| taken LITERALLY, i.e. store-pointer nodes p
      with cStore(p, base) -- the object's own base id used as a store's VALUE
      operand. This is ALWAYS 0 for every object base, by construction: in
      extract.go, cStore's value operand always comes from `b.node(ssaValue)`,
      while object base ids only ever come from `b.obj(key, t)`; both draw
      from the same monotonic `b.nNodes` counter but never collide, so no
      cStore constraint's value operand can ever equal an object base id. This
      is a structural fact of the id scheme, not a soundfix-specific one. It
      means the entry's remembered "storesWhereValue[base]" framing cannot
      have meant the field applied directly to a base id -- confirmed, not
      merely suspected, by re-reading extract.go's node()/obj() allocators.

  (b) the mechanistically real writer-candidate set: every node v (0..N) that
      ground truth (ptsBatch, the batch/Andersen oracle) says can alias &base
      (base ∈ ptsBatch[v]), unioned with storesWhereValue[v] for each such v
      -- i.e. store-pointers that write a REFERENCE to some v that itself
      points to the merged base. |union| = U. How many of U's members end up
      `active` after an ISOLATED forward-track of &base (demandContents(base)
      + run() on a scratch rsm instance, no other seed) is "reached". This is
      the (N-store-pointers vs. M-reached)-shaped pair the entry described
      from memory as "91 across 32 functions, reaches 5" -- measured directly
      here instead.

  Distinct-SSA-function span: for each p in the union, p's originating
  ssa.Value is recovered by inverting builder.nodeOf (node id -> ssa.Value,
  built once from `b.nodeOf`), then resolved to its enclosing function via a
  `Parent() *ssa.Function` type assertion (covers ssa.Instruction values and
  ssa.Parameter). Some store-pointer nodes have no resolvable ssa.Value
  (synthesized/tuple/global nodes) or a nil Parent (package-level); those are
  reported as "unresolved", not silently dropped.

WHAT THIS MEASURES, HONESTLY:
  - This is NOT literally "storesWhereValue[base]" in the sense the field name
    reads (that quantity is always 0, see (a) above, a structural fact of the
    id scheme rather than a discovery about soundfix).
  - This IS the mechanistically-relevant analog: for the missing objects'
    bases, the honest measured pair is (store-pointer candidate count U,
    forward-reached count) = (192-196, 126-128) for the two large hub bases
    that dominate the missing-object count, and (~191-192, 0-1) for the
    smaller merged bases in third place. Neither pair is "91 vs 5" -- the
    entry's remembered numbers do not match what is measured here, on either
    axis (universe size ~2x larger; reached fraction for the DOMINANT bases is
    ~65%, not ~5%; only the THIRD-ranked, smaller bases show the near-total
    failure the remembered "5 of 91" shape suggests).
  - The function-span figure (108-112 distinct functions per base, 7
    unresolved each) IS newly and directly measured here (not re-derived from
    memory); it was NOT measured in the original E36 session and the "32
    functions" figure in the entry is unverified against this instrumentation.
  - Reconciling exactly what quantity produced "91 store-pointers across 32
    functions, reaches 5" in the original E36 session was not attempted
    further -- the id-scheme fact in (a) rules out the literal reading, and
    (b) is the closest well-defined analog this session could construct and
    verify by direct measurement. The entry's qualitative claim ("forward-
    tracking a single &base reaches only a small fraction of its writers, for
    at least some of the merged objects behind these misses") IS supported:
    the third-ranked, smaller merged bases show fwd-reached 0-1 out of ~192.
    The claim that the DOMINANT bases (mheap, workType) are similarly
    unreachable is NOT supported -- they are ~65% reached, not ~5%.
