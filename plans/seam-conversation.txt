❯ what constitutes a "seam" in a design or program?                             

⏺ A seam is a place where you can change a program's behavior without editing
  code at that place. The definition is Michael Feathers' (Working Effectively 
  with Legacy Code), and the precision matters: it's not "an extension point" or
  "a boundary" loosely. It's specifically a location where substitution is
  possible from somewhere else.

  The two-part structure

  Every seam has two pieces, and people conflate them:

  1. The seam — the location whose behavior can vary.
  2. The enabling point — the place where you decide which behavior is in
  effect.

  These are usually different locations. That separation is the whole point. If
  you had to edit the seam itself to change behavior, it wouldn't be a seam;
  it'd just be code you modify.

    enabling point                    seam
    (where you choose)                (where behavior varies)
          │                              │
          ▼                              ▼
    NewService(realDB)  ───────►  s.db.Query(...)
    NewService(fakeDB)            (unchanged; behaves
                                   differently per db)

  Feathers' three kinds, in modern terms

  - Preprocessing seams — C/C++ #define/#include substitution. Enabling point is
  the preprocessor. (Rare outside C.)
  - Link seams — swap a library, object file, or classpath entry at build/link
  time. Enabling point is the build config. In Go: build tags, replacing a
  package via the module graph, go:linkname.
  - Object seams — pass a different implementation behind an interface. Enabling
  point is wherever the object is constructed or injected. This is the dominant
  kind in Go: an interface parameter, a function value (func(...)), a struct
  field holding a dependency.

  ★ Insight ─────────────────────────────────────
  In Go, the cleanest seam is an interface accepted as a parameter, not
  returned. The enabling point moves to the caller (dependency injection),
  so the dependent code never names a concrete type. A package that takes
  io.Reader has a seam; one that calls os.Open internally does not.
  ─────────────────────────────────────────────────

  The discriminating test

  Ask: "Can I make this code use different behavior here without touching this 
  line?"

  - s.db.Query(...) where db is an injected interface → seam (enabling point:
  the constructor).
  - sql.Open(...) called inline → not a seam (the only way to change it is to
  edit the line).

  A direct call to a concrete function is the canonical non-seam. The behavior
  is welded in at the call site.

  Why it matters

  Seams are where you pull a system apart and reassemble it differently:

  - Testing — they're where test doubles go. "Untestable" code usually means "no
  seam between the logic and its dependency."
  - Substitution — they're the joints along which you can replace an
  implementation (the CLAUDE.md "verify by substitution" test is literally
  asking is there a seam wide enough that every call site can use the unified 
  function?).
  - Change isolation — a good seam confines the blast radius of a change to one
  enabling point.

  ★ Insight ── connection to wile-goast ───────────
  Your FCA boundary analysis is seam analysis turned diagnostic. A
  "false boundary" is a structural seam that splits code that's actually
  one concept (the seam exists but shouldn't bear load). A "recommended
  boundary" / min-cut split proposes a *new* seam where cohesion is low
  and coupling crosses cleanly. Feathers asks "where CAN I cut?"; your
  tooling asks "where SHOULD the cut be, given the concept lattice?"
  Same geometry, opposite direction.
  ─────────────────────────────────────────────────

  One caveat on candor: "seam" gets used loosely in casual design talk to mean
  any module boundary or API surface. That's a weaker, vaguer sense. Feathers'
  definition is the load-bearing one because it gives you a concrete test
  (substitution without local edit) rather than a vibe. When precision matters,
  use his.

  the enabling point is the instantiation. That's Wadler, "Theorems for Free"
  (line 283, already cited). Frame seam as parametricity you can instantiate,
  cite Feathers as the practitioner's name for it, and it fits the skill instead
